## 1. 引言

### 1.1 编写目的

本文档定义" BearPi 睡眠环境调节与卧床行为监测系统"第一版的功能需求、非功能需求、数据与接口需求及验收标准，作为：

- 五人分工开发的对齐基准（各模块按同一需求编号交付）
- 第一阶段评审和最终演示验收的打勾依据
- 后续阶段变更需求的基线（变更需在本文件上修订并升版本号）

### 1.2 项目背景

面向普通居家睡眠场景，制作一套原型系统：通过床体压力/动作信息判断使用者是否在床、是否出现明显体动；采集卧室温湿度、光照等环境数据；在设定条件满足时控制简单的环境设备；将状态、历史数据和控制记录显示在网页上。

项目重点是把"**感知—判断—调节—记录—展示**"做成一个能现场演示的完整闭环，而不是单独展示传感器读数。

### 1.3 术语与缩写

| 术语 | 含义 |
|------|------|
| 床体节点 | BearPi-HM Nano + E53_SC2（MPU6050）+ FSR 压力传感器 |
| 环境节点 | BearPi-HM Nano + E53_IA1（温湿度、光照），可选 CO₂ |
| 执行器 | 低压直流风扇（配 MOSFET 驱动模块、独立电源） |
| IoTDA | 华为云物联网设备接入服务（IoT Device Access） |
| 物模型 | IoTDA 中定义的设备属性/命令模型，本项目含 `BedService`、`EnvService` 两个 service |
| AMQP 订阅 | 后端主动连接 IoTDA（5671）消费属性上报，本项目主数据通道 |
| HTTP 回调 | 后端 `POST /iot/callback`，带 nonce/timestamp/signature 签名校验的备用推送入口，当前仅打日志、不落库 |
| 防抖 | 状态切换需持续稳定超过设定时间才生效，避免波动导致状态反复 |
| 回差 | 开/关阈值之间留出的区间（如 30℃ 开、28℃ 关），避免风扇频繁启停 |

## 2. 项目概述

### 2.1 系统一句话范围

系统在床体和环境两类感知节点采集数据，经华为云 IoTDA 传输到后端服务入库，按明确阈值规则控制风扇并在网页上展示实时状态、历史曲线与控制记录——**它是环境与卧床行为的记录展示系统，不是医疗睡眠监测设备**。

### 2.2 明确不做的内容（第一版红线）

1. 不进行医疗诊断，不判断疾病或给出医疗结论
2. 不做睡眠分期、深睡/浅睡判定或睡眠质量医学评分
3. 不做睡眠呼吸暂停筛查，不采集或推断心率、血氧
4. 不把短时间少量样本的对比结果宣传为"改善睡眠"的因果证明
5. 不在第一版堆叠多个复杂节点、复杂 AI 模型和大量执行器
6. 不让 AI 直接控制硬件（自动控制必须走明确阈值规则）
7. ST1 提示板未验证通过前，不列为核心依赖

### 2.3 用户与典型使用场景

**用户**：项目演示评审者；潜在场景为普通家庭卧室使用者。

**典型场景（即最终演示脚本，详见任务书第八章）**：

1. 演示者躺上模拟床垫 → 网页显示"在床"；离开 → 防抖时间后显示"离床"
2. 轻拍床垫 → 网页出现一条体动事件
3. 改变环境传感器附近温度/光照 → 网页实时更新
4. 温度达到阈值 → 风扇自动开启；恢复后关闭；网页显示控制状态与触发原因
5. 拔掉传感器或断开节点 → 网页显示传感器异常/设备离线，而不是看似正常的数据
6. 展示历史曲线与事件记录

### 2.4 约束条件

| 约束 | 内容 |
|------|------|
| 周期 | 约 6 周，第一阶段为立项与需求准备 |
| 团队 | 5 人，按模块分工，接口连接（见 3.2） |
| 硬件 | 已有 BearPi-HM Nano 主板及 E53 拓展板；FSR、CO₂、风扇、驱动模块等需采购 |
| 通信 | 已定路线 B：节点 →(MQTT/TLS 8883)→ 华为云 IoTDA →(AMQP 订阅 5671)→ 后端；另有 HTTP 推送回调 `POST /iot/callback`（签名校验，当前不落库）；演示依赖外网，需备手机热点兜底 |
| 后端部署 | 一台局域网电脑运行后端 + SQLite 数据库 |

## 3. 系统总体结构

### 3.1 架构与数据流

```

                 ├─ MQTT/TLS ─→ 华为云IoTDA ─┬─ AMQP订阅(主) ────→ 后端服务 ─→ SQLite
环境节点 env-01 ─┘                           ├─ HTTP推送(备，签名)→ 后端服务
                                             │
                                             └← 命令下发(fan_control，待实现) ←┘
```

### 4.2 需求详述

**FR-01 在床/离床判断**
- 输入：MPU6050 三轴加速度（上报属性 `accelX` / `accelY` / `accelZ`）+ FSR 压力（采购到货后接入）
- 处理：节点侧计算 `motionState`（床垫静止/运动）、`motionCount10s`、`motionPowerPeak`；阈值判断 + 防抖（默认 10 s，可配置）；状态切换才上报变化
- 输出：上述体动属性写入 `bed_readings`；`bed_state ∈ {in_bed, out_of_bed}` 由 `motionState` + FSR 压力派生，后端按上报序列记录变化时间（变化点单独记录待实现）
- 验收：上床→网页显示"在床"；离开→防抖时间后显示"离床"；连续演示数据留存

**FR-02 体动记录**
- 输出：`motionState`（床垫静止/运动）+ `motionCount10s`（近 10 s 体动次数）+ `motionPowerPeak`（近 10 s 运动功率峰值）；强度用 `motionPowerPeak` 表达，不划分 0–3 等级，不识别睡眠阶段
- 验收：轻拍床垫→`motionState` 变为"运动"→网页 5 s 内出现一条体动事件

**FR-03 环境采集上报**
- 指标：温度（℃）、湿度（%RH）、光照（lux）、`env_status`（环境节点状态）；上报周期 ≤ 30 s
- 验收：改变传感器环境→网页实时更新；异常值有处理策略（成员2 文档化）

**FR-05 风扇控制**
- 链路：后端 → IoTDA 命令下发 → 节点 MOSFET 驱动 → 风扇
- 先做开关，调速为增强；必须有独立电源和匹配的驱动模块
- 验收：手动与规则两种方式均可控制；每次控制有记录

**FR-07 通信（经云）**
- 节点 MQTT over TLS（8883）属性上报；断线自动重连
- 验收：断网 1 分钟→恢复后自动重连续传，网页正确标记期间离线

**FR-08/09 后端接收与存储**
- 校验（已实现）：按属性名映射取值，数值字符串、浮点数转整数自动转换；转换失败写 NULL 并告警；未知 service 或未映射属性跳过并告警，不中断消费
- 校验（待实现）：device_id 已注册、时间戳在合理范围、非法数据返回错误码且整条拒写；重复推送按 `device_id + event_time` 幂等去重
- 存储（已实现）：`env_readings`、`bed_readings` 两张宽表，每次上报写一行，含 `event_time`（平台事件时间）与 `received_at`（本地接收时间）
- 存储（待实现）：`device` 设备信息、`control_record` 控制记录（含触发原因）、`rule_config` 规则配置、卧床状态变化点
- 验收：构造缺字段/错类型数据测试通过（当前预期：缺字段写 NULL、错类型转 NULL 并告警）；四类数据均可经接口取回（查询接口待实现）

**FR-10 规则服务**
- 规则形式：`metric ≥ threshold_on → 开；metric ≤ threshold_off → 关`（回差防频繁启停）
- 示例：rule-1 温度 ≥ 30℃ 开风扇，≤ 28℃ 关
- 每次触发写控制记录，reason 必须含规则号与当时数值；阈值可经接口修改
- 验收：温度越限→风扇动作且记录含触发原因

**FR-11 查询接口**
- 设备列表与在线状态、最新数据、历史曲线（降采样）、卧床状态/事件、控制记录、规则配置读写
- 详见配套接口草案第 3 章
- 验收：前端按接口文档逐项调用成功

**FR-13 异常展示**
- 传感器异常（sensor_status=fault）、设备离线（超时未上报）、网络中断，网页必须显式标识
- 验收：拔传感器/断网→网页显示异常/离线，不显示看似正常的旧数据

## 5. 非功能需求

| 编号 | 需求 | 指标 |
|------|------|------|
| NFR-01 | 上报周期 | 环境数据 ≤ 30 s；卧床状态变化即时；体动事件 ≤ 5 s |
| NFR-02 | 在线判定 | 超过 2 个上报周期无数据 → 离线 |
| NFR-03 | 防抖 | 默认 10 s，可配置 |
| NFR-04 | 端到端延迟 | 经云链路节点动作 → 网页更新 ≤ 10 s |
| NFR-05 | 数据量 | 单表 < 10 万条，第一版全量保留 |
| NFR-06 | 部署 | 后端 + SQLite 单机一键启动 |
| NFR-07 | 可靠性演示 | 断外网时网页须显示全链路离线（而非假数据），现场备手机热点 |

## 6. 数据需求

- 数据库：SQLite（WAL 模式），文件默认 `data/iot.db`，可用 `SQLITE_PATH` 覆盖
- 已实现 2 张宽表：
  - `env_readings`：`temperature`、`humidity`、`light`、`env_status`
  - `bed_readings`：`accel_x` / `accel_y` / `accel_z`、`motion_state`、`motion_count_10s`、`motion_power_peak`
- 待建 3 张表：`device`（设备信息/在线状态）、`control_record`（含触发原因）、`rule_config`（阈值配置）
- 时间戳：`event_time`（平台事件时间）与 `received_at`（本地接收时间）均为 ISO 8601 带时区文本，**不是 Unix 秒**
- 单位在字段定义中固定（℃、%RH、lux、ppm）；当前表结构**没有 CO₂ 列**，纳入第一版需新增列（改表），不能靠预留 NULL 免改表
- 表结构以 `src/backend/storage.py` 的 `SCHEMA` 与 `SERVICE_TABLES` 为准；配套草案补齐后同步

## 7. 接口需求

- 节点 ↔ IoTDA：MQTT/TLS（8883），物模型 service：`BedService`、`EnvService`；命令 `fan_control` 尚未实现
- IoTDA → 后端：
  - 主通道：AMQP 订阅（`amqps://<host>:5671`，AccessKey/AccessCode 鉴权，断线 1–15 s 指数退避重连）
  - 备通道：HTTP 推送 `POST /iot/callback`（`nonce`/`timestamp`/`signature` 签名校验，当前仅打日志、不落库，需公网 HTTPS）
- 后端 → 前端：HTTP `/api/v1/*`（查询接口待实现）；统一响应 `{code, message, data}`。现有接口为 `POST /iot/callback`（返回 `{code, message}`）和 `GET /`（健康检查）
- 详细接口与错误码见配套草案第 3 章（草案待补，暂以后端代码为准）
